> 记录 IR-05（视觉感知事件）、IR-06（语音告警事件）、IR-07（预测性维护）  
> 三个创新点的技术实现逻辑与关键设计决策  
> 实现日期：2026-07-04

---

## 一、IR-05 视觉感知事件（IN-04 视觉感知与联动）

### 创新逻辑

传统路灯只有"开关"和"亮度"两个维度。本系统将路灯升级为具备 **"视觉观察能力"** 的智能终端 —— 每个路灯通过 AI 摄像头感知路面动态，识别行人、车辆、异常事件。

### 关键设计

**1. 传感器联动生成（非凭空模拟）**

视觉事件不是独立随机产生的，而是基于现有遥测传感器的数据触发：

| 传感器数据 | 触发事件 | 概率 | 设计原因 |
|-----------|---------|------|----------|
| PIR=1（检测到人体） | 行人检测 | 30% | 有人经过才有行人的视觉事件，因果关系合理 |
| trafficFlow>10 | 车辆通行 | 40% | 车流量高的区域才有车辆识别事件 |
| 随机 | 异常停车/危险场景 | 5% | 稀有事件，低概率模拟偶发异常 |

这种设计的核心优势 **"假设摄像头在持续工作，每当传感器感知到环境变化时才可能产生对应的事件"** —— 用传感器数据驱动视觉逻辑，而非虚构数据。

**2. MQTT 主题隔离**

```
遥测通道：  streetlight/{deviceId}/telemetry    → Telemetry 表
视觉通道：  streetlight/{deviceId}/vision/event  → VisionEvent 表
指令通道：  streetlight/{deviceId}/command       → ControlCommand 表
```

每条通道独立发布、独立订阅、独立入库，互不干扰。`MqttSubscriber` 通过 `topic.endsWith()` 路由分拣。

**3. 置信度设计**

真实 AI 模型永远输出概率而非确定值。模拟数据生成 60%-99% 的置信度范围：
- 行人/车辆检测：70%-99%（目标明显，识别较准）
- 异常停车/危险场景：60%-99%（场景复杂，波动更大）

前端用颜色区分：绿色(≥90%) / 橙色(70%-90%) / 红色(<70%)。

## 二、IR-06 语音告警事件（IN-05 语音告警与播报）

### 创新逻辑

路灯不仅是"照明工具"，还承载**公共服务信息播报**职能。在雨雾天气、道路施工、夜间节能等场景下，路灯自动广播信息提醒行人和车辆。

### 关键设计

**1. 双源语音事件模型**

| 来源 | 触发方式 | 类型 | 场景 |
|------|---------|------|------|
| MockDataGenerator 随机 | 10% 概率，从 8 条中文内容池随机选择 | 播报/广播/警告 | 日常播报、天气提醒、自检通知 |
| DecisionEngine 策略联动 | 策略命中且 extraActions.voiceAlert=true | 警告 | AI 自动决策后的事件记录 |

**2. 策略联动是关键创新**

当 AI 策略引擎(DecisionEngine)匹配到一条策略并执行动作时，同时检查该策略的 `extraActions.voiceAlert` 字段。如果为 true，则**自动产生一条语音告警事件**，记录"哪个设备、什么策略被触发、执行了什么操作"。

这实现了 **"AI 决策 → 自动控制 → 语音记录" 的完整闭环**。

**3. 类型自动分类**

```
内容含"预警"/"异常"  → type="警告"  (danger)
内容含"请"           → type="播报"  (primary)
其他                 → type="广播"  (info)
```

## 三、IR-07 预测性维护与健康评分（IN-06 预测性维护）

### 创新逻辑

传统运维是 **"坏了才修"（被动响应）**，本系统实现 **"在坏之前预警"（主动预测）**。每台路灯设备每天自动获得一个 0-100 分的健康评分，分数持续下降即为预警信号。

### 关键设计

**1. 四维综合评分模型**

| 维度 | 权重 | 数据来源 | 计算逻辑 |
|------|------|----------|----------|
| 离线频次 | 30% | alarm_record 表 | 近7天 OFFLINE 告警次数 |
| 通信质量 | 25% | telemetry 表 | 近24h 上报间隔标准差 vs 理想值(300s) |
| 指令响应率 | 25% | control_command 表 | 近7天 有 ackAt / 总指令数 |
| 传感器异常率 | 20% | device.latestData | 5 个传感器字段是否在合理范围内 |

**2. ACK 机制（前提依赖）**

在实现健康评分前，必须先建立 **"指令确认(ACK)"** 机制：

```
后端发指令 → MQTT → 设备执行 → 设备回 ACK → 后端更新 control_command.ackAt
```

- `MqttSubscriber` 订阅 `streetlight/+/command/ack` topic
- `MockDataGenerator` 以 90% 概率模拟 ACK 回复
- ACK 机制使得"指令响应率"维度可用

这种设计反映了真实物联网特征 **不完美是常态** —— 丢包、延迟、离线是正常的，100% 响应率反而不可信。

**3. 健康等级划分**

```
90-100  🟢 优秀 — 设备状态极佳
70-89   🟡 良好 — 正常运行，可继续观察
50-69   🟠 一般 — 开始出现异常
30-49   🔴 较差 — 建议尽快维修
0-29    ⛔ 危险 — 随时可能故障
```

**4. 降分原因可追溯**

每个维度的评分附带降分原因，如：
- "近7天离线3次（07-01、07-03、07-04），电源或通信模块可能不稳定"
- "遥测上报间隔波动较大（标准差=95s），无线信号可能受干扰"
- "12条指令中有3条无设备确认（响应率75%），通信可能存在问题"

运维人员不需要猜测"为什么这个设备的分数低"，原因直接可见。

## 四、三个创新点的关联

```
                    ┌──────────────────────┐
                    │   MockDataGenerator   │ ← 同一个模拟器
                    │   每5分钟循环一次       │
                    └──────┬───────────────┘
                           │
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
      遥测数据          视觉事件          语音事件
   (telemetry表)   (vision_event表)  (voice_event表)
          │
          ▼
   DecisionEngine
          │
          ├──→ 匹配策略 → 下发控制指令 → control_command表
          │                          │
          │                    ACK 机制 ──→ 命令确认
          │                          │
          ├──→ voiceAlert=true  → voice_event表 (策略联动语音)
          │                          │
          └──→ 数据积累 ──→ HealthScoreTask (每天凌晨)
                              │
                    4维评分 → device.health_score
                              │
                    前端展示 ← health API
```

**数据流总结**：遥测 + 视觉 + 语音三条数据源通过 MQTT 并行上报，策略引擎利用遥测数据做自动决策，ACK 机制保证指令可追溯，健康评分为所有数据提供"质量评分"层，最终在前端统一呈现。

## 五、技术架构优势

1. **MQTT 协议解耦**：模拟数据和真实硬件共用同一套 topic 协议，只需改配置 `mock.enabled = false` 即可切换
2. **MyBatis-Plus 通用 Mapper**：视觉/语音事件的 Service 无需写 SQL，继承 `ServiceImpl<Mapper, Entity>` 即可
3. **定时任务分离**：MockDataGenerator(模拟)、HeartbeatMonitorTask(心跳)、HealthScoreTask(健康) 各自独立，互不依赖
4. **前端事件中心**：视觉/语音事件统一在 EventCenter 页面展示，设备详情页集成健康评分卡片
