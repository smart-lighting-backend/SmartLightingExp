# 后端配合需求 — 前端性能优化

## 背景

前端已完成以下性能优化（本次改动）：
- Dashboard 页面缓存 + API 去重 + 请求缓存
- 7 个监控页面增加自动刷新
- KeepAlive 缓存避免页面重建

现有后端接口已基本满足需求，以下是可选优化项，按优先级排列。

---

## P1：建议新增 — 设备列表后端分页（有就做，没有也能跑）

### 原因

当前 `src/views/Devices.vue` 调用 `POST /api/devices/list` 时传入 `pageSize: 10000`，一次性拉取全部设备到前端做客户端分页。数据量增长后会影响首屏加载速度。

### 现状

`POST /api/devices/list` 接口已支持 `pageNum` 和 `pageSize` 参数，后端应已具备分页能力。

### 改动

前端改为按页请求（`pageSize: 12`），不做改动即可使用。后端无需额外开发。

### 可否不做

可以，前端当前也能跑。只是数据量超过几千条时建议配上。

---

## P2：建议新增 — 轻量地图数据接口（长期推荐）

### 接口

```
GET /api/devices/map-locations
```

### 返回数据

```json
{
  "code": 200,
  "data": [
    {
      "deviceId": "SL-001",
      "name": "南门-01",
      "location": "106.5622,29.5621",
      "status": 1,
      "area": "A区",
      "healthScore": 98.5
    }
  ]
}
```

### 原因

Dashboard 地图只需要 6 个字段，但当前 `POST /api/devices/list` 返回全量字段（含 heartbeat、topicPrefix 等地图无关数据）。千级设备下响应体积可减少约 60%。

### 可否不做

可以。前端已用 `fetchAllDevicesForMap()` 封装好了，后端加了这个接口后前端替换一下 URL 即可。

---

## P3：建议新增 — 告警未处理计数接口（可选）

### 接口

```
GET /api/alarms/count?status=ACTIVE
```

### 返回数据

```json
{
  "code": 200,
  "data": { "count": 5 }
}
```

### 原因

前端顶栏告警角标每 45 秒刷新一次，当前用 `POST /api/alarms/list { status: 'ACTIVE', pageSize: 1 }` 取 total 字段来获取计数。专用计数接口更轻量。

### 可否不做

可以。当前用 list 接口取 total 也能正常运��。

---

## 总结

| 优先级 | 接口 | 必要性 |
|--------|------|--------|
| P1 | 设备列表分页 | 已有接口已支持，无需额外开发 |
| P2 | `GET /api/devices/map-locations` | 推荐，千级设备时有明显收益 |
| P3 | `GET /api/alarms/count?status=ACTIVE` | 锦上添花，当前方案也能跑 |

**三项都可以不做**，前端当前功能完整可用。做了之后性能和流量会更优。
