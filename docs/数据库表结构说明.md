# 数据库表结构说明

> 创建日期：2026-07-04
> 数据库：`smart_lighting_db`（阿里云 RDS MySQL 8.4）
> 当前实际存在 **13 张表**（设计文档中提到的 `role_permission` 未建表）

## 一、device（设备台账表）

**作用**：路灯设备的"身份证"，记录每盏路灯的静态属性、实时状态快照和配置参数。是整个系统的核心主数据表。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGINT PK | 自增主键 |
| `device_id` | VARCHAR(50) UNIQUE | 设备唯一编号，对应 MQTT Topic 中的 deviceId |
| `name` | VARCHAR(100) | 设备名称，如"路灯-01" |
| `area` | VARCHAR(50) | 所属区域，如"A区"、"B区"，有独立索引 |
| `location` | VARCHAR(255) | 安装位置（经纬度或地址描述） |
| `status` | TINYINT | 状态：0-停用，1-在线，2-离线，3-异常 |
| `health_score` | DECIMAL(5,2) | 健康分（0~100），综合评估设备运行质量 |
| `topic_prefix` | VARCHAR(100) | MQTT 主题前缀，默认 `streetlight` |
| `last_heartbeat_at` | DATETIME(3) | 最近一次心跳时间，用于离线检测 |
| `latest_data` | JSON | 最新遥测快照（JSON 字段），供前端快速展示 |
| `last_manual_at` | DATETIME(3) | 最近一次手动操作时间，用于 30 分钟手动锁定 |
| `rated_power` | DECIMAL(10,2) | 额定功率（W），能耗估算基础参数，默认 150 |
| `enabled` | TINYINT(1) | 是否启用，0-停用，1-启用 |
| `deleted` | TINYINT(1) | 逻辑删除标记，0-正常，1-已删除 |
| `create_time` | DATETIME(3) | 创建时间 |
| `update_time` | DATETIME(3) | 更新时间（自动更新） |

**关键索引**：`uk_device_id`（唯一），`idx_area`，`idx_status`

**数据流向**：
- 写入：设备注册时创建，心跳上报时更新 `last_heartbeat_at` 和 `latest_data`
- 读取：设备列表、仪表盘统计、策略引擎遍历设备、能耗计算遍历设备
- `status` 由 HeartbeatMonitorTask 定时更新（在线↔离线）

## 二、telemetry（遥测数据表）

**作用**：记录路灯传感器采集的环境数据，是系统中数据量最大的流水表。每条记录对应一次传感器上报。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGINT PK | 自增主键 |
| `device_id` | VARCHAR(50) | 设备 ID |
| `illuminance` | DECIMAL(10,2) | 光照强度（lux），策略引擎最核心的决策依据 |
| `temperature` | DECIMAL(5,2) | 温度（℃），高温告警来源 |
| `humidity` | DECIMAL(5,2) | 湿度（%） |
| `pm25` | DECIMAL(5,2) | PM2.5 浓度 |
| `aqi` | INT | 空气质量指数 |
| `pir` | TINYINT | 人体红外感应，0-无人，1-有人 |
| `traffic_flow` | INT | 车/人流量（计数器值） |
| `collected_at` | DATETIME(3) | 数据采集时间（设备侧时钟） |
| `create_time` | DATETIME(3) | 系统入库时间 |

**关键索引**：`idx_device_collected (device_id, collected_at)`

**数据流向**：
- 写入：MockDataGenerator 定时模拟上报 / 真实设备通过 MQTT 上报 → MqttSubscriber 入库
- 读取：设备详情页遥测历史查询
- **注意**：策略引擎不直接读此表做决策（用 `device.latest_data` 快照），本表用于历史追溯

---

## 三、control_command（控制指令表）

**作用**：记录每一次下发给路灯的控制指令，包括手动和自动。是能耗计算的核心数据源。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGINT PK | 自增主键 |
| `device_id` | VARCHAR(50) | 设备 ID |
| `action` | VARCHAR(20) | 指令动作：`ON`（开灯）、`OFF`（关灯）、`DIMMING`（调光） |
| `brightness` | INT | 亮度值（0~100），仅 DIMMING 时有值 |
| `source` | VARCHAR(20) | 指令来源：`MANUAL`（手动）、`AUTO`（策略引擎）、`EMERGENCY`（应急） |
| `operator` | VARCHAR(50) | 操作人（手动时记录用户名） |
| `status` | VARCHAR(20) | 执行状态：`SENT`（已发送）、`ACKED`（设备已确认）、`FAILED`（失败）、`TIMEOUT`（超时） |
| `issued_at` | DATETIME(3) | 指令下发时间 |
| `ack_at` | DATETIME(3) | 设备回执时间 |
| `result_detail` | VARCHAR(255) | 执行结果详情 |

**关键索引**：`idx_device_issued (device_id, issued_at)`，`idx_status`

**数据流向**：
- 写入：用户手动操作 / DecisionEngine 自动决策 / MqttPublisher 下发
- 读取：EnergyCalcTask 按 `issued_at` 时间加权计算平均亮度和亮灯时长
- `status` 由 MqttSubscriber 在收到设备 ACK 回执后更新

---

## 四、alarm_record（告警记录表）

**作用**：记录设备异常事件的全生命周期（发生→确认→恢复），支持告警分类和级别管理。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGINT PK | 自增主键 |
| `device_id` | VARCHAR(50) | 设备 ID |
| `type` | VARCHAR(30) | 告警类型：`OFFLINE`（离线）、`OVER_TEMP`（高温）、`VISION_ABNORMAL`（视觉异常）、`HEALTH_LOW`（健康分低） |
| `level` | VARCHAR(10) | 告警级别：`MAJOR`（主要）、`MINOR`（次要）、`CRITICAL`（严重） |
| `status` | VARCHAR(20) | 告警状态：`ACTIVE`（活跃）、`RECOVERED`（已恢复）、`ACKNOWLEDGED`（已确认） |
| `reason` | VARCHAR(255) | 告警原因描述 |
| `start_at` | DATETIME(3) | 告警开始时间 |
| `recover_at` | DATETIME(3) | 恢复时间（NULL 表示尚未恢复） |
| `handler` | VARCHAR(50) | 处理人 |

**关键索引**：`idx_device_start (device_id, start_at)`，`idx_type`，`idx_level`

**数据流向**：
- 写入：HeartbeatMonitorTask 检测离线 → 创建告警；设备重连 → 自动恢复
- 读取：仪表盘告警统计（`COUNT WHERE status='ACTIVE'`）、告警列表/详情页
- 恢复逻辑：设备重新上报心跳时，HeartbeatMonitorTask 将 ACTIVE 告警标记为 RECOVERED

---

## 五、lighting_policy（照明策略表）

**作用**：定义路灯自动控制的规则，是 AI 策略引擎的"规则库"。每条策略描述"在什么条件下执行什么动作"。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGINT PK | 自增主键 |
| `name` | VARCHAR(100) | 策略名称，如"夜间弱光模式" |
| `policy_type` | VARCHAR(20) | 策略类型：`THRESHOLD`（阈值触发）、`TIME`（时段触发）、`SCENE`（场景触发） |
| `conditions` | JSON | 条件 JSON，如 `{"lux_lt":50,"time_range":"22:00-06:00"}` |
| `action` | VARCHAR(50) | 执行动作：`ON`、`OFF`、`DIMMING(70)` |
| `priority` | INT | 优先级（1 最高，10 最低），多策略命中时取最高优先级 |
| `enabled` | TINYINT(1) | 是否启用，0-禁用，1-启用 |
| `deleted` | TINYINT(1) | 逻辑删除 |
| `effective_time` | VARCHAR(100) | 生效时段描述（前台展示用） |
| `create_time` | DATETIME(3) | 创建时间 |

**关键索引**：`idx_policy_type`，`idx_enabled`

**数据流向**：
- 管理：用户通过策略管理页面 CRUD
- 执行：DecisionEngine 每次收到遥测后读取所有启用的策略（`enabled=1 AND deleted=0`），按 priority 排序匹配

---

## 六、decision_log（策略决策日志表）

**作用**：记录策略引擎每一次评估的输入和输出，用于事后审计"为什么灯亮了/灭了"。是调试策略的"黑匣子"。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGINT PK | 自增主键 |
| `device_id` | VARCHAR(50) | 设备 ID |
| `input_snapshot` | JSON | 决策时的遥测快照（光照、温度、PIR 等） |
| `matched_policy` | VARCHAR(100) | 命中的策略名称（NULL 表示无策略命中） |
| `action_taken` | VARCHAR(50) | 最终执行动作（如 `DIMMING(60)`、`SKIP`） |
| `result` | VARCHAR(20) | 执行结果：`EXECUTED`、`SKIPPED`、`LOCKED`、`NO_MATCH` |
| `create_time` | DATETIME(3) | 记录时间 |

**关键索引**：`idx_device_time (device_id, create_time)`，`idx_result`，`idx_create_time`

**数据流向**：
- 写入：DecisionEngine 每次评估后写入（无论是否执行）
- 读取：策略调试、问题排查
- `result=SKIPPED`：设备状态已满足策略目标，无需重复下发
- `result=LOCKED`：设备处于手动锁定期间，跳过自动控制
- `result=NO_MATCH`：没有策略条件匹配

**作用**：记录路灯摄像头 AI 视觉识别结果，用于安防联动和行人/车辆统计。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGINT PK | 自增主键 |
| `device_id` | VARCHAR(50) | 设备 ID |
| `event_type` | VARCHAR(30) | 事件类型：`PERSON`（行人）、`VEHICLE`（车辆）、`ABNORMAL_STAY`（异常停留）、`INTRUSION`（入侵） |
| `confidence` | DECIMAL(5,2) | 识别置信度（0~100） |
| `snapshot_ref` | VARCHAR(255) | 抓拍快照的文件路径/URL |
| `occurred_at` | DATETIME(3) | 事件发生时间 |
| `create_time` | DATETIME(3) | 系统入库时间 |

**关键索引**：`idx_device_occurred (device_id, occurred_at)`，`idx_event_type`

**数据流向**：
- 写入：AI 视觉模块通过 MQTT/API 上报识别结果
- 读取：安防告警联动、异常停留告警
- 当前状态：**表已建但暂无数据**，属于预留功能

- 当前状态：**表已建但暂无数据**，属于预留功能

## 九、energy_record（能耗统计表）

**作用**：**日粒度**的设备级能耗统计，每天每条启用的设备一行。是仪表盘能耗卡片和报表图表的直接数据源。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGINT PK | 自增主键 |
| `device_id` | VARCHAR(50) | 设备 ID |
| `record_date` | DATE | 统计日期 |
| `on_duration_min` | INT | 亮灯时长（分钟），有指令时从第一条指令算起 |
| `avg_brightness` | DECIMAL(5,2) | 时间加权平均亮度（0~100），由调光指令序列计算 |
| `estimated_kwh` | DECIMAL(10,4) | 估算用电量（千瓦时）= rated_power/1000 × on_hours × brightness/100 |
| `saving_rate` | DECIMAL(5,2) | 节能率（%）= 100 - avg_brightness |
| `carbon_reduction` | DECIMAL(10,4) | 碳减排估算（kg CO₂）= (基准-实际) × 排放因子 0.785 |
| `create_time` | DATETIME(3) | 创建时间 |

**关键索引**：`idx_device_date (device_id, record_date)`，`idx_record_date`

**计算逻辑**（由 EnergyCalcTask 每日 23:55 执行）：
1. 读 `control_command` 表中当日该设备的调光指令
2. 按 `issued_at` 排序，时间加权计算平均亮度
3. 无调光指令 → 默认 avg_brightness=100%，saving_rate=0%（不虚报节能）
4. kWh = 额定功率(kW) × 亮灯小时 × 亮度系数
5. 节能率 = 100 - avg_brightness
6. Upsert 写入（同一天同一设备记录已存在则更新）

**数据流向**：
- 写入：EnergyCalcTask 定时计算 / `POST /api/dashboard/energy/calc` 手动触发
- 读取：仪表盘 stats/todayEnergy/energySavingRate、能耗趋势、月度/年度统计、分区占比

## 十、audit_log（操作审计日志表）

**作用**：记录所有关键操作，满足安全可信控制（IR-11 安全要求）。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGINT PK | 自增主键 |
| `operator` | VARCHAR(50) | 操作人用户名 |
| `action` | VARCHAR(30) | 操作类型：`LOGIN`（登录）、`DEVICE_ADD/DELETE`（设备增删）、`THRESHOLD_SET`（阈值设置）、`CONTROL_ON/OFF`（开关灯）、`DIMMING`（调光）、`POLICY_UPDATE`（策略变更）等 |
| `target_type` | VARCHAR(20) | 操作目标类型：`DEVICE`、`POLICY`、`THRESHOLD`、`SYSTEM` |
| `target_id` | VARCHAR(50) | 操作目标 ID（如设备 ID、策略 ID） |
| `detail` | VARCHAR(500) | 操作详情描述 |
| `result` | VARCHAR(10) | 操作结果：`SUCCESS` / `FAIL` |
| `ip_address` | VARCHAR(50) | 操作来源 IP |
| `operated_at` | DATETIME(3) | 操作时间 |

**关键索引**：`idx_operator_time (operator, operated_at)`，`idx_action_time (action, operated_at)`，`idx_operated_at`

**数据流向**：
- 写入：用户登录、设备控制、策略修改等关键操作时由 Service 层写入
- 读取：系统日志页面（SystemLog.vue）查询展示

## 十一、user（系统用户表）

**作用**：记录系统登录用户信息，每个用户属于一个角色。支持软删除和登录审计。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGINT PK | 自增主键 |
| `username` | VARCHAR(50) UNIQUE | 用户名（登录账号） |
| `password` | VARCHAR(255) | 密码（BCrypt 加密存储） |
| `real_name` | VARCHAR(50) | 真实姓名 |
| `phone` | VARCHAR(20) | 手机号 |
| `email` | VARCHAR(100) | 邮箱 |
| `department` | VARCHAR(50) | 所属部门 |
| `area_code` | VARCHAR(20) | 管辖区域编码 |
| `role_id` | BIGINT | 角色 ID，关联 `role.id`（每个用户只属于一个角色） |
| `enabled` | TINYINT(1) | 是否启用，0-禁用，1-启用 |
| `last_login_ip` | VARCHAR(50) | 最近登录 IP |
| `last_login_time` | DATETIME(3) | 最近登录时间 |
| `deleted` | TINYINT(1) | 逻辑删除标记（非 NULL，默认 0） |
| `create_time` | DATETIME(3) | 创建时间 |
| `update_time` | DATETIME(3) | 更新时间 |

**关键索引**：`uk_username`（唯一），`idx_role_id`

## 十二、role（角色表）

**作用**：定义系统角色，如"管理员"、"操作员"、"观察员"。通过 `role_code` 在代码中进行权限判断。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGINT PK | 自增主键 |
| `name` | VARCHAR(50) | 角色名称，如"管理员"、"操作员"、"观察员" |
| `role_code` | VARCHAR(20) UNIQUE | 角色编码：`ADMIN`、`OPERATOR`、`VIEWER` |
| `description` | VARCHAR(255) | 角色描述 |
| `create_time` | DATETIME(3) | 创建时间 |

**关键索引**：`uk_role_code`（唯一）

**⚠️ 注意**：角色与权限之间没有关联表。`role_permission` 表在设计文档中提及但实际未创建。当前权限控制可能是通过硬编码的 `role_code` 在拦截器/代码层面判断（如 `ADMIN` 可以访问所有接口，`VIEWER` 只能读取）。

## 十三、permission（权限定义表）

**作用**：定义系统所有可用的操作权限，采用树形结构（模块级 + 操作级）。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGINT PK | 自增主键 |
| `parent_id` | BIGINT | 父权限 ID，NULL=模块级（如"设备管理"），非 NULL=操作级（如"创建设备"） |
| `name` | VARCHAR(50) | 权限名称（显示用），如"创建设备" |
| `permission_code` | VARCHAR(50) UNIQUE | 权限编码，格式 `模块:操作`，如 `device:create` |
| `type` | VARCHAR(10) | 类型：`MODULE`（模块级菜单/分组）、`ACTION`（具体操作） |
| `description` | VARCHAR(200) | 权限说明 |
| `create_time` | DATETIME(3) | 创建时间 |

**关键索引**：`uk_permission_code`（唯一），`idx_parent_id`

**⚠️ 注意**：本表中虽然定义了细粒度的权限码（如 `device:create`），但由于缺少 `role_permission` 关联表，这些权限码未与角色绑定。当前系统实际使用的是基于 `role_code` 的粗粒度权限控制（在 `JwtInterceptor` 中按角色编码判断接口访问权限）。
