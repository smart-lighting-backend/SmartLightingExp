## 一、后端新增接口规划

需要新增 2 个接口（均在 `DashboardController` 中）：

### 1. GET /api/dashboard/energy/yearly-stats?year=2026

**用途**：替换 Analytics 顶部 4 个硬编码卡片。

**SQL 逻辑**：
```sql
-- 年度总能耗（kWh）
SELECT SUM(estimated_kwh) FROM energy_record WHERE YEAR(record_date) = ?

-- 年度节省量（kWh）= Σ(额定功率 × 亮灯小时 × (1 - 平均亮度/100) - estimated_kwh)
-- 简化：Σ(saving_rate / 100 * estimated_kwh / (avg_brightness / 100) * ...) 太复杂
-- 实际做法：基准能耗 = rated_power/1000 * on_duration_min/60，节省量 = 基准 - estimated_kwh
-- 但 energy_record 表没有存基准能耗，所以后端需要用 saving_rate 反推：
--   节省量 = estimated_kwh / ((100 - saving_rate)/100) - estimated_kwh
--   或更简单的近似：节省量 ≈ estimated_kwh * saving_rate / (100 - saving_rate)

-- 实际上可以这样（从 EnergyCalcTask 逻辑可知）：
--   saving_rate = 100 - avg_brightness
--   baseline_kwh = ratedKw * onDurationH
--   estimated_kwh = baseline_kwh * (avg_brightness / 100)
-- 所以节省量 = baseline_kwh - estimated_kwh = baseline_kwh * saving_rate / 100
-- 又 estimated_kwh = baseline_kwh * (100 - saving_rate) / 100
-- 即 baseline_kwh = estimated_kwh * 100 / (100 - saving_rate)
-- 节省量 = estimated_kwh * 100 / (100 - saving_rate) * saving_rate / 100
--       = estimated_kwh * saving_rate / (100 - saving_rate)

-- 这太绕了。最简单做法：sum estimated_kwh * saving_rate / avg_brightness...
-- 其实直接两遍查：多查一次 device 表拿 rated_power，在 Java 里算。

-- 碳减排量（吨）
SELECT SUM(carbon_reduction) FROM energy_record WHERE YEAR(record_date) = ?
-- （carbon_reduction 单位是 kg，前端显示时 / 1000 转吨）

-- 平均在线率：直接复用 stats() 接口的 onlineRate 逻辑
-- 比较去年数据（用于 "同比降低 12.3%" 等副标题）
```

**返回结构**：
```json
{
  "code": 200,
  "data": {
    "year": 2026,
    "totalKwh": 51438.5,
    "savedKwh": 16820.3,
    "carbonReductionKg": 8400.0,
    "avgOnlineRate": "95.0",
    "lastYear": {
      "totalKwh": 58350.2,
      "savedKwh": 14100.0,
      "carbonReductionKg": 7200.0,
      "avgOnlineRate": "92.9"
    }
  }
}
```

**实现要点**：
- year 参数可选，默认当前年份
- lastYear 为 null 时不显示同比信息（前端判空即可）
- 当某年无数据时，返回全 0 值而非报错
- saving_rate = 0 时（无调光指令），节省量也为 0（这是合理的）

### 2. GET /api/dashboard/energy/monthly?year=2026

**用途**：替换月度能耗柱状图的随机数。

**SQL 逻辑**：
```sql
SELECT 
  MONTH(record_date) AS month,
  SUM(estimated_kwh) AS consumption,
  -- 节省量同理用 saving_rate 反推
FROM energy_record 
WHERE YEAR(record_date) = ?
GROUP BY MONTH(record_date)
ORDER BY month
```

**返回结构**：
```json
{
  "code": 200,
  "data": {
    "year": 2026,
    "months": ["1月","2月",...,"12月"],
    "consumption": [4200,3800,...,5100],
    "savings": [800,950,...,1200]
  }
}
```

**实现要点**：
- 没有数据的月份补 0
- consumption 和 savings 是一一对应的数组

---

### 3. GET /api/dashboard/energy/district?year=2026

**用途**：替换分区能耗占比硬编码饼图。

**SQL 逻辑**：
```sql
SELECT 
  d.area,
  SUM(er.estimated_kwh) AS total_kwh
FROM energy_record er
JOIN device d ON d.device_id = er.device_id
WHERE YEAR(er.record_date) = ?
  AND d.deleted = 0
GROUP BY d.area
ORDER BY total_kwh DESC
```

**返回结构**：
```json
{
  "code": 200,
  "data": [
    { "name": "A区", "value": 32.5 },
    { "name": "B区", "value": 25.0 },
    { "name": "C区", "value": 20.0 },
    { "name": "D区", "value": 13.0 },
    { "name": "E区", "value": 9.5 }
  ]
}
```

**实现要点**：
- null/空 area 归入 "未分配"
- value 使用 `estimated_kwh` 而非百分比，前端 ECharts 饼图会自动计算占比
- 如果只有少数几个区，饼图也正常展示

## 六、EnergyTrend 逐时数据问题（P2，暂不实施）

### 当前逻辑回顾

`GET /api/dashboard/energy-trend` 三步：

1. 查 `energy_record` 表，汇总今日所有设备的能耗得到一个总数字 `todayTotal`
2. 同上查上周同一天，得到 `lastWeekTotal`
3. 用硬编码权重数组把这两个数字"拆"回 24 小时：

```java
double[] weights = {
    0.08, 0.07, 0.06, 0.05, 0.04, 0.03, // 0-5时
    0.02, 0.01, 0.01, 0.01, 0.01, 0.02, // 6-11时
    0.02, 0.02, 0.01, 0.01, 0.01, 0.02, // 12-17时
    0.03, 0.05, 0.08, 0.10, 0.10, 0.09  // 18-23时 晚高峰
};
// 每小时的"能耗" = todayTotal × weights[i]
```

### 问题

| 方面 | 问题 |
|------|------|
| 数据来源 | `energy_record` 只有日粒度，不存在逐时字段 |
| 分布方式 | 权重数组是硬编码的"典型路灯能耗曲线"，不会变化 |
| 真实性 | 今天下雨天黑早 18:00 亮灯，但曲线仍按 19:00 才爬升 |
| 变化性 | 无论阴天/晴天、工作日/周末，曲线形状永远不变 |
| 对比意义 | 今日 vs 上周两条折线完全同形，只差一个总量系数 |

### 根因

`energy_record` 表是日粒度的（一个设备一天一行），没有逐时数据。无法从日粒度反推真实小时曲线。

### 如果要改成真实逐时数据（P2）

不查 `energy_record`，直接用 `control_command` 表的调光指令序列还原：

```
for each hour 0..23:
  找到该小时内最后一条调光指令的 brightness
  如果没有，沿用上一条指令的 brightness（或默认 100%）
  该小时能耗 = brightness/100 × ratedPower/1000 × 1h
  汇总所有设备
```

代价：需要 JOIN device 表拿 rated_power，计算量更大。但如果设备没有指令，按满功率算是合理的。

### 当前阶段决定

- 先修复 Analytics 的硬编码/随机数问题（P0）
- EnergyTrend 的权重拆解法暂时保留，但前端去掉无数据时的随机降级
- 真实逐时还原作为 P2，等数据量大、有真实对比需求时再做
