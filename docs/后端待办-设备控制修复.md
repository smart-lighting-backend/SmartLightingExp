# 后端待办 — 设备控制问题修复

> 创建日期：2026-07-03
> 背景：走查手动控制和自动控制（DecisionEngine）全链路，发现 5 个问题，包括策略种子数据逻辑错误、Mock 下手动控制假成功、设备状态不更新等。
> 以下改动需要等前端伙伴确认当前分支修改范围后再进行。

## 1. THRESHOLD 策略种子数据逻辑错误（P0）

### 现状

`02_seed_data.sql:57`：
```sql
('光照联动自动开关', 'THRESHOLD', '{"lux_lt": 50, "lux_gt": 200}', 'ON', 1, 1, 0, '全天')
```

`DecisionEngine.java:113-117` 将所有 conditions 按 **AND 逻辑** 求值，`lux_lt=50 AND lux_gt=200` 意味着光照强度需要同时 <50 且 >200，**逻辑上不可能**，该策略永远不会触发。

### 修复方案

**方案 A（推荐）**：拆成两条策略，分别处理开灯和关灯：

```sql
-- 光照低于 50 → 开灯（优先级 1）
('光照低自动开灯', 'THRESHOLD', '{"lux_lt": 50}', 'ON', 1, 1, 0, '全天'),

-- 光照高于 200 → 关灯（优先级 2）
('光照高自动关灯', 'THRESHOLD', '{"lux_gt": 200}', 'OFF', 2, 1, 0, '全天'),
```

**方案 B（简单）**：只修一条，仅保留开灯：
```sql
('光照联动自动开关', 'THRESHOLD', '{"lux_lt": 50}', 'ON', 1, 1, 0, '全天')
```

**改动位置**：`database/02_seed_data.sql` 第 57 行

### 影响面
- 低，只影响种子数据，不改动引擎代码
- 建议走方案 A，两条策略 + 不同优先级，让自动控制攻防都能工作

## 2. Mock 下手动控制假成功（P1）

### 现状

`api/devices.js` 的 `controlDevice()` Mock 数据为 `null`：
```javascript
export function controlDevice(deviceId, payload) {
  return safeCall(
    () => request.post(`/api/devices/${deviceId}/control`, payload),
    null,  // ← Mock 数据为 null
    `POST /api/devices/${deviceId}/control`
  )
}
```

后端不可用时，`safeCall` 返回 `{ code: 200, msg: 'mock', data: null }`，`ManualControlModal` 的 try 块认为成功，显示 ✅ 但实际上后端的 control_command 未插入、MQTT 未发布、lastManualAt 未更新、审计日志未写。

### 修复方案

给 `controlDevice` 添加有意义的标准 Mock 响应：

```javascript
export function controlDevice(deviceId, payload) {
  return safeCall(
    () => request.post(`/api/devices/${deviceId}/control`, payload),
    { code: 200, msg: 'mock', data: { id: Date.now(), deviceId, ...payload, status: 'SENT', source: 'MANUAL', issuedAt: new Date().toISOString() } },
    `POST /api/devices/${deviceId}/control`
  )
}
```

**改动位置**：`D:\Vue-Workspace\smart_lighting_vue\src\api\devices.js:285-291`

### 影响面
- 仅前端文件，不影响后端
- Mock 模式下用户能看到指令"成功"，但需要配合设备状态更新的 Mock 才能看到效果

## 3. 手动控制后设备状态不更新（P2）

### 现状

`ControlController.java:109-113` 手动控制成功时只更新了 `lastManualAt`：
```java
.set(Device::getLastManualAt, LocalDateTime.now());
```

**没有更新 `device.status` 和 `device.latestData`**。手动"关灯"后 Dashboard 上设备仍然是"在线"，latestData 里的亮度还是旧值。前端看不到手动控制的效果。

### 修复方案

在 `ControlController.java` 的手动控制成功分支，给 `deviceMapper.update` 增加字段同步：

```java
// 同步设备状态
String newStatus;
if ("OFF".equals(request.getAction())) {
    newStatus = "OFF";
} else if ("ON".equals(request.getAction())) {
    newStatus = "ON";
} else {
    newStatus = "DIMMING(" + request.getBrightness() + ")";
}

deviceMapper.update(null,
    new LambdaUpdateWrapper<Device>()
        .eq(Device::getDeviceId, deviceId)
        .set(Device::getLastManualAt, LocalDateTime.now())
        .set(Device::getStatus, "OFF".equals(request.getAction()) ? 0 : 1)  // OFF→停用, ON/DIMMING→在线
        .set(Device::getLatestData, buildLatestDataJson(deviceId, request)));
```

注意：需要额外考虑
- `status=0`（停用）是否适合表示"关灯"？建议新增字段或扩展语义
- `latestData` 的 JSON 快照更新需包含 brightness

**改动位置**：`ControlController.java:109-113`

### 影响面
- 中。后端需新增一个构建 latestData JSON 的辅助方法
- 需与前端确认：关灯后 `status` 字段用什么值（0=停用 或 新增 4=关灯）

## 4. DecisionEngine MQTT 发布失败未记录（P3）

### 现状

`DecisionEngine.executeAction()` 的 catch 只打日志，不记录失败的 control_command 和 decision_log：
```java
catch (Exception e) {
    log.error("[{}] DecisionEngine executeAction failed: {}", deviceId, e.getMessage());
}
```

导致自动化控制失败时完全不可见，无法排查。

### 修复方案

catch 块中补一条失败记录：

```java
catch (Exception e) {
    log.error("[{}] DecisionEngine executeAction failed: {}", deviceId, e.getMessage());
    // 补充：记录失败的 control_command
    ControlCommand failedCmd = new ControlCommand();
    failedCmd.setDeviceId(deviceId);
    failedCmd.setAction(action);
    failedCmd.setSource("AUTO");
    failedCmd.setStatus("FAILED");
    failedCmd.setIssuedAt(LocalDateTime.now());
    failedCmd.setResultDetail("MQTT下发失败-" + e.getMessage());
    controlCommandMapper.insert(failedCmd);
    
    // 补充：记录失败的 decision_log
    DecisionLog failLog = new DecisionLog();
    failLog.setDeviceId(deviceId);
    failLog.setMatchedPolicy(policyName);
    failLog.setActionTaken(action);
    failLog.setResult("MATCH_FAILED");
    failLog.setInputSnapshot(buildSnapshotJson(telemetry));
    decisionLogMapper.insert(failLog);
}
```

**改动位置**：`DecisionEngine.java:209-212`

### 影响面
- 低。只增强日志记录，不改业务逻辑

## 5. Mock 模式自动控制链路不可见（P4）

### 现状

```
MockDataGenerator(每5分钟) → MQTT broker → MqttSubscriber → DecisionEngine
```

MQTT broker 未运行时整条链路断裂，用户无从知晓自动控制是否尝试过。

### 修复方案

**方案一（后台日志）**：`DecisionEngine.evaluate()` 增加日志，在方法入口和退出时打印设备ID和匹配结果，方便查日志：
```java
log.info("[{}] DecisionEngine evaluate start: lux={}, pir={}", 
    deviceId, telemetry.getIlluminance(), telemetry.getPir());
```

**方案二（前端可见）**：在 Dashboard 或设备详情页增加 decision_log 查询接口，让用户能看到最近的决策记录：
```
GET /api/decision-log/latest/{deviceId}?limit=10
```

**改动位置**：`DecisionEngine.java:49`（方案一）/ 新增 API（方案二）

### 影响面
- 方案一：低，只加日志
- 方案二：中，需新增接口 + 前端页面改动
