# 设备在线状态与离线告警 — 后端实现说明

> 对应功能：FR-06 设备在线状态监控、FR-07 设备离线告警
> 涉及后端文件：`MqttSubscriber.java`、`HeartbeatMonitorTask.java`、`AlarmRecordService.java`
> 前端仅需理解数据变化规律，**无需修改代码**。

---

## 一、设备在线状态（device.status）

### 1.1 状态取值

| status | 含义 | 说明 |
|:------:|------|------|
| 0 | 停用 | 设备手动停用（enabled=false），不参与心跳检测 |
| **1** | **在线** | 最近收到该设备的遥测数据，status 自动置为 1 |
| **2** | **离线** | 超过 5 分钟未收到遥测，系统自动置为 2 |
| 3 | 异常 | 手动标记，暂不自动变更 |

### 1.2 状态变更规则（前端需要知道）

```
收到遥测数据
  └→ device.status = 1（在线）
  └→ device.lastHeartbeatAt = 当前时间

超过 300 秒（5 分钟）未收到任何遥测
  └→ device.status = 2（离线）

设备重新上报遥测
  └→ device.status = 1（在线）
  └→ device.lastHeartbeatAt = 更新
```

**关键结论：前端获取设备列表时，`status` 和 `lastHeartbeatAt` 字段现在是动态变化的**，不再是固定不变的种子数据。

## 二、离线告警（alarm_record）

### 2.1 告警字段说明

| 字段 | 值 | 说明 |
|------|----|------|
| `type` | `OFFLINE` | 离线告警类型 |
| `level` | `MAJOR`（严重） | 离线告警严重级别 |
| `status` | `ACTIVE` → `RECOVERED` | 见下方生命周期 |
| `reason` | 文本描述 | 自动生成，含最后心跳时间和离线阈值 |
| `startAt` | 时间戳 | 告警生成时间（即检测到离线的时刻） |
| `recoverAt` | 时间戳 | 告警恢复时间（设备重新上报遥测的时刻） |
| `handler` | null | 离线告警不支持手动处理 |

### 2.2 告警生命周期

```
设备持续 5 分钟无遥测
  └→ 定时任务检测到超时
       ├→ device.status = 2
       └→ 检查无 ACTIVE 的 OFFLINE 告警
            └→ alarm_record 新增一条（status=ACTIVE）

设备恢复遥测上报
  └→ MqttSubscriber 收到数据
       ├→ device.status = 1
       ├→ device.lastHeartbeatAt = now
       └→ 自动恢复离线告警
            └→ alarm_record.status = RECOVERED
            └→ alarm_record.recoverAt = 当前时间
```

### 2.3 告警去重规则

- 同一设备、同一类型（OFFLINE）、同一状态（ACTIVE）只能存在一条告警
- 恢复后再离线，重新生成新告警
- 前端的告警列表接口 `GET /api/alarms/page` 查询时，可能出现多条同一设备的 OFFLINE 告警（一条已 RECOVERED，一条新的 ACTIVE）

## 三、数据变化对前端的影响

### 3.1 设备列表页

现有前端代码已经正确支持所有状态。`STATUS_MAP` 中的映射：

```js
{
  0: { label: '停用',  cls: 'disabled' },
  1: { label: '在线',  cls: 'online'    },
  2: { label: '离线',  cls: 'offline'   },
  3: { label: '异常',  cls: 'warning'   },
}
```

设备对象中 `lastHeartbeatAt` 字段现在是实时刷新的，不等于设备创建时间。

### 3.2 告警中心页

现有前端代码已支持以下告警值：

| 维度 | 前端支持的取值 | 本功能使用的值 |
|------|--------------|---------------|
| 告警类型 | `OFFLINE` / `FAULT` / `SECURITY` / `VISION` | **`OFFLINE`** |
| 告警级别 | `CRITICAL` / `MAJOR` / `WARNING` / `INFO` | **`MAJOR`** |
| 告警状态 | `ACTIVE` / `ACKNOWLEDGED` / `RECOVERED` | **`ACTIVE`** → **`RECOVERED`** |

### 3.3 仪表盘

`GET /api/dashboard/stats` 返回的统计数据中：

| 字段 | 说明 |
|------|------|
| `alertCount` | 未处理告警数（alarm_record 中 status=ACTIVE 的记录数） |
| `onlineRate` | 在线率 = 在线设备数 / 总设备数 |

### 3.4 交互建议

- 设备列表可定期刷新（如每 30~60 秒），以反映最新的在线/离线状态变化
- 告警列表可按 `status=ACTIVE` 过滤，快速查看未处理的离线告警
- 设备详情页的"最后心跳"字段已有显示，现在它是实时更新的

## 四、后端定时任务参数

```yaml
heartbeat:
  detection-interval-ms: 60000       # 离线检测每 60 秒执行一次
  offline-threshold-seconds: 300     # 判定离线阈值（秒）
  startup-delay-ms: 120000           # 应用启动后 2 分钟才开始检测
```

前端不需关心这些参数，但理解检测粒度有助于设计刷新策略：
- 设备离线后最长 **5 分钟 + 60 秒** 才会被标记为离线并生成告警
- 设备恢复后**立即**（下一次遥测到达时）恢复在线状态和告警
