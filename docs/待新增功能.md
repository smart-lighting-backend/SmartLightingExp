## 烧录验证与修复记录（2026-07-22）

### 问题一：策略引擎覆盖 F1 手动开灯

**现象**：F1 短按开灯后，后端策略引擎立即下发 OFF 命令覆盖。

**根因**：`MqttSubscriber.java` 的 `inManual` 检查只看数据库 `device.manualMode` 字段。设备 F1 按键发出的 `led_source=MANUAL` 在遥测 JSON 中被完全忽略。

**修复**：`MqttSubscriber.java` 第 135-140 行，新增从遥测 JSON 读取 `led_source` 字段的判断——若为 `"MANUAL"` 则跳过 `DecisionEngine.evaluate()`。

### 问题二：按钮响应慢 + F1 长按失效

**现象**：F1/F2 短按延迟明显（1-2 秒），F1 长按 3 秒几乎不可用。

**根因**：`button_check()` 在主循环外循环中执行，仅每 **1.5 秒**检查一次。短按时间窗口极窄，长按需跨 2 次外循环才能触发。

**修复**：将 `button_check()` 从外循环移到子循环（每 **250ms**），检测频率提升 **6 倍**。新增 `g_last_lux` 缓存光照值供子循环使用。

### F1 长按行为说明

F1 长按已移除（硬件按键抖动导致 ISR 重复触发，长按不可靠）。替代方案：需要重连 MQTT 时按 RESET 键重启设备。

### 问题三：前端不显示手动控制状态（2026-07-22 补充修复）

**现象**：F1/F2 按键后设备处于手动模式，但前端不显示"手动控制"。

**根因**：前端通过 `device.manualMode` 和 `device.manualExpireAt` 数据库字段判断手动状态。后端 `MqttSubscriber` 识别 `led_source=MANUAL` 后仅跳过了策略引擎，没有把 `manualMode=true` 写入数据库。

**修复**：`MqttSubscriber.java` 第 157-165 行，当 `deviceSideManual=true` 时同步写入 `manualMode=true, manualExpireAt=now+30min`。

## 一、主板红色 LED 状态指示（GPIO_2）

### 1.1 功能说明

利用主板上红色 LED（GPIO_2），通过不同闪烁模式直观反映设备运行状态。

### 1.2 状态定义

| 阶段 | LED 行为 | 含义 |
|------|----------|------|
| 上电启动 | 快闪（亮 200ms / 灭 200ms） | 设备正在启动，WiFi 配网中 |
| WiFi 已连接 | 慢闪（亮 500ms / 灭 500ms） | WiFi 连接成功，正在连 MQTT |
| MQTT 已连接 | 呼吸灯（PWM 渐变，2 秒周期） | 正常运行 |
| 收到远程命令 | 急闪 3 下（亮 100ms / 灭 100ms × 3） | MQTT 命令确认 |
| WiFi/MQTT 断开 | 快闪（亮 200ms / 灭 200ms） | 故障告警，正在重连 |

### 1.3 技术方案

**GPIO 初始化**：在 `smartlighting_task()` 初始化阶段（PWM 初始化之后）加：

```c
// 主板红色 LED 初始化 (GPIO_2)
IoSetFunc(WIFI_IOT_IO_NAME_GPIO_2, WIFI_IOT_IO_FUNC_GPIO_2_GPIO);
GpioSetDir(WIFI_IOT_IO_NAME_GPIO_2, WIFI_IOT_GPIO_DIR_OUT);
GpioSetOutputVal(WIFI_IOT_IO_NAME_GPIO_2, WIFI_IOT_GPIO_VALUE0);  // 初始灭
```

**LED 控制方式**：
- 快闪/慢闪/急闪：在主循环中用计数器驱动 GPIO 高低切换（主循环每 ~500ms 迭代一次，精度足够）
- 呼吸灯：需要用 PWM（`WIFI_IOT_PWM_PORT_PWM2`），Hi3861 支持 6 路 PWM，GPIO_2 复用为 PWM2_OUT

**PWM 呼吸灯实现**：

```c
// GPIO_2 → PWM2
IoSetFunc(WIFI_IOT_IO_NAME_GPIO_2, WIFI_IOT_IO_FUNC_GPIO_2_PWM2_OUT);
PwmInit(WIFI_IOT_PWM_PORT_PWM2);
// 在主循环中动态调整占空比实现呼吸效果
```

**修改范围**：仅 `smartlighting.c`，新增约 40 行 LED 控制代码，不需要改其他文件。

### 1.4 实现后效果

```
上电 ────────────────────────────────────────────── 正常运行
 │                                                   │
 ├─ 红灯快闪 ──→ WiFi 连上 ──→ 红灯慢闪 ──→ MQTT 连上 ──→ 红灯呼吸
 │   (配网中)                    (连MQTT中)              (正常运行)
 │                                                       │
 └──────────── WiFi/MQTT 断开时 ←── 红灯快闪 ←────────────┘
               (故障告警)
```

运维人员看一眼 LED 就知道设备是否正常运行，无需连串口或登录后台。

## 二、F1 按键交互（GPIO_11）

### 2.1 功能说明

利用用户按键 F1，实现现场物理按键控制。

### 2.2 按键功能定义

| 操作 | 行为 | 说明 |
|------|------|------|
| **短按**（< 1 秒） | 手动开关灯 | 灯灭 → 开灯 100%；灯亮 → 关灯；进入 MANUAL 模式 |
| **长按**（≥ 3 秒） | 断开 MQTT 重新连接 | 主动断开 MQTT → 主循环自动重连 → 如 WiFi 已失效需 AT 重新配网 |

### 2.3 技术方案

**GPIO 中断注册**：

```c
// F1 按键初始化 (GPIO_11)
IoSetFunc(WIFI_IOT_IO_NAME_GPIO_11, WIFI_IOT_IO_FUNC_GPIO_11_GPIO);
GpioSetDir(WIFI_IOT_IO_NAME_GPIO_11, WIFI_IOT_GPIO_DIR_IN);
IoSetPull(WIFI_IOT_IO_NAME_GPIO_11, WIFI_IOT_IO_PULL_UP);  // 内部上拉
GpioRegisterIsrFunc(WIFI_IOT_IO_NAME_GPIO_11,
                    WIFI_IOT_INT_TYPE_EDGE,
                    WIFI_IOT_GPIO_EDGE_FALL_LEVEL_LOW,
                    F1_pressed_callback, NULL);
```

**短按/长按检测方案**：

由于 Hi3861 的中断回调上下文不能做复杂操作，采用"ISR 记录时间戳 + 主循环轮询判定"的方式：

1. ISR 回调中：记录按下时刻 `g_f1_press_ticks`，置标志位 `g_f1_pending = 1`
2. 主循环中（每 ~500ms 迭代）：检查标志位，读当前 GPIO 电平
   - 仍按下 + 距按下时间 ≥ 3 秒 → 判定长按
   - 已释放 + 距按下时间 < 1 秒 → 判定短按
3. 用 `GpioGetInputVal()` 读取当前电平（低=按下，高=释放）

**短按处理**：
```c
if (短按) {
    if (g_led_status == 0) {
        pwm_set_brightness(100);  // 开灯
    } else {
        pwm_set_brightness(0);    // 关灯
    }
    g_led_source    = LED_SOURCE_MANUAL;
    g_manual_remain = MANUAL_TIMEOUT_SEC;
}
```

**长按处理（断开 MQTT 重连）**：
```c
if (长按) {
    printf("[BTN] 长按: 断开 MQTT, 准备重连\r\n");
    g_mqtt_connected = 0;
    NetworkDisconnect(&g_network);  // 断开 MQTT
    g_f1_long_trig = 0;            // 立即清零, 避免阻塞下次按键 ← Bug修复
    // MQTT 断开后主循环的断线重连逻辑会自动恢复
    // 如果 WiFi 本身已失效，重连持续失败 → 红灯快闪提示 AT 配网
}
```

**注意**：此处仅断开 MQTT 层，不操作 WiFi。WiFi 断开重连需调用阻塞函数 `WifiConnect()`（耗时 15-30 秒），在当前主循环中执行会卡死设备。WiFi 级别的重连留给 P3 统一处理。

### 2.4 注意事项

- Hi3861 每个 GPIO 只能注册一个中断回调，不需要动态切换边沿（只在主循环中轮询释放状态）
- 需要软件去抖：主循环每 ~500ms 迭代一次天然去抖，50ms 内抖动不会影响
- F1 和 F2 的中断回调互相独立，可以同时使用

### 2.5 状态同步到 Web 端（关键）

按键触发的手动控制状态变更，必须在当前遥测周期内**立即上报**，不能等下一个 3 秒周期。否则 Web 端看到的状态会有最多 3 秒延迟，影响远程监控的实时性。

**实现方式**：在按键处理逻辑执行完毕后，立即调用一次 `publish_telemetry()`：

```c
// 短按处理
if (短按) {
    // ... 开关灯、切 MANUAL 模式 ...
    publish_telemetry(lux);  // 立即上报，不等下次循环
}

// 长按处理
if (长按) {
    // ... 断开 WiFi、准备重连 ...
    publish_telemetry(lux);  // 上报当前状态后再断连
    g_mqtt_connected = 0;
    NetworkDisconnect(&g_network);
}
```

遥测 JSON 中已包含 `led_source` 字段（`"AUTO"` 或 `"MANUAL"`）和 `led_status`、`brightness`，前端可直接从遥测数据中解析控制模式。

### 2.6 实现后效果

```
巡检人员在设备现场，手机没电了，需要关灯：
  → 短按 F1 → 灯灭
  → 固件立即上报 telemetry（led_source=MANUAL, led_status=OFF, brightness=0）
  → Web 端 Dashboard 实时看到设备变为"手动关灯"
  → 30 分钟后自动恢复边缘决策

设备 MQTT 连接异常，需要手动触发重连：
  → 长按 F1 3 秒 → 设备断开 MQTT
  → 红灯快闪 → 主循环自动重连
  → 如果 WiFi 正常 → 几秒后恢复在线
  → 如果 WiFi 已失效 → 红灯持续快闪 → 需 AT 重新配网
```

## 三、NFC 碰一碰查看设备状态（NT3H1201）

### 3.1 功能说明

手机碰一下设备 NFC 天线区域，自动显示设备运行状态信息。

**注意**：不做碰一碰自动配网（子功能 B），仅做状态查看。原因：
- 碰一碰配网需要 `StartNetCfg()` API，OpenHarmony SDK 可用性需确认
- 当前已有 AT 串口配网 + MQTT config Topic 远程改 WiFi，再来一种配网方式必要性不高

### 3.2 技术方案

NT3H1201 是 NXP 的 NFC Forum Type 2 Tag 芯片，带 I2C 接口。MCU 通过 I2C 写入数据，手机通过 NFC 读取数据，两边共享同一片 EEPROM（1904 字节）。

**I2C 通信**：NT3H1201 挂在 I2C1 总线上（GPIO_0=SDA, GPIO_1=SCL），与 E53_SC1 的 BH1750 共用同一条 I2C 总线。7 位地址 `0x55`（与 BH1750 的 `0x23` 不冲突）。

**数据写入格式**：在 NT3H1201 的用户存储区写入一个 NDEF 格式的 URI 记录，或者直接写 JSON 字符串（手机 NFC 读取后以纯文本显示）。

推荐使用 NDEF Smart Poster 格式，手机读取后显示为卡片样式：

```
设备: Real_CS_001
状态: 在线 | 离线
模式: AUTO | MANUAL
光照: 342.5 lux
LED: ON (100%)
WiFi: OnePlus 15 5F06
最后上报: 2 秒前
```

**主循环中定期更新**：每 10 秒（约 3 个主循环周期）通过 I2C 写入最新状态到 NT3H1201，手机碰一碰时读到的是最近一次写入的数据。

### 3.3 关键注意事项

- **I2C 总线共享**：BH1750（0x23）和 NT3H1201（0x55）在同一 I2C1 上，地址不冲突，但写入 NT3H1201 时需要确保不影响 BH1750 的读取时序
- **EEPROM 写入寿命**：NT3H1201 的 EEPROM 写入寿命约 10 万次，10 秒写一次意味着连续工作约 11.5 天就达到寿命上限。**需要改用 SRAM 区（64 字节，无写入寿命限制）**或降低写入频率到 60 秒一次（寿命约 69 天连续运行）
- **最佳方案**：使用 NT3H1201 的 SRAM 区作为 NFC 数据镜像（64 字节足够存放状态 JSON），SRAM 写入无限寿命，通过 I2C 写入 SRAM 后 NFC 也可以读取

### 3.4 实现后效果

```
运维人员在设备现场巡检，不清楚这台设备是什么状态：
  → 掏出手机，解锁，碰一下主板 NFC 天线区域
  → 手机屏幕自动弹出信息：
      ┌────────────────────────────────┐
      │  🔦 智慧路灯 Real_CS_001       │
      │  ────────────────────────────  │
      │  状态: 🟢 正常运行             │
      │  模式: AUTO（自动边缘决策）     │
      │  光照: 342.5 lux               │
      │  LED:  ON（100% 亮度）         │
      │  WiFi: OnePlus 15 5F06         │
      │  更新: 刚刚                     │
      └────────────────────────────────┘
  → 不需要登录任何系统，不需要蓝牙配对
  → iPhone 和安卓都能用（NFC 标准读取）
```

## 五、F2 按键短按调光（GPIO_12）

### 5.1 功能说明

利用用户按键 F2，实现现场物理按键循环切换 LED 亮度。

### 5.2 按键功能定义

| 操作 | 行为 | 说明 |
|------|------|------|
| **短按**（< 1 秒） | 循环切换亮度 | 20% → 50% → 100% → 20% → ...；切换后进入 MANUAL 模式 |

F2 不做长按功能，保持简洁。

### 5.3 技术方案

与 F1 完全相同的"ISR 记录时间戳 + 主循环轮询"模式，注册 GPIO_12 的下降沿中断。

**亮度循环逻辑**：

```c
// 亮度档位数组
static const int brightness_levels[] = {20, 50, 100};
static int brightness_index = 0;  // 当前档位索引

// 短按处理
if (f2_短按) {
    brightness_index = (brightness_index + 1) % 3;
    int new_brightness = brightness_levels[brightness_index];
    pwm_set_brightness(new_brightness);
    g_brightness    = new_brightness;
    g_led_status    = (new_brightness > 0) ? 1 : 0;
    g_led_source    = LED_SOURCE_MANUAL;
    g_manual_remain = MANUAL_TIMEOUT_SEC;
    publish_telemetry(lux);  // 立即同步到 Web
    printf("[BTN] F2 短按: 亮度 → %d%%\r\n", new_brightness);
}
```

### 5.4 注意事项

- 初始默认亮度 100%，`brightness_index` 应从 2（100%）开始，第一次按 F2 切到 20%
- 如果当前是 0%（灯灭），按 F2 直接跳到 20%
- 与 F1 按键的短按开关灯逻辑互补：F1 关心开/关，F2 关心亮度精细调节

### 5.5 实现后效果

```
现场人员觉得灯太亮了：
  → 按一下 F2 → 亮度降到 50% → Web 端实时更新
  → 再按一下 → 亮度降到 20%
  → 再按一下 → 亮度回到 100%
  → 30 分钟后自动恢复边缘决策
```

## 六、收到 WiFi 配置后等待重启（简化方案）

### 6.1 设计思路

不做自动 WiFi 重连，硬件收到新配置后仅写入 Flash 并停止遥测上报，等待运维人员到现场按 RESET 重启。前后端配合展示"等待重启"状态。

### 6.2 完整业务流程

```
前端设备详情页
  │
  ├─ 用户输入新 WiFi SSID + 密码
  ├─ 前端弹二次确认：
  │   "修改 WiFi 配置后，设备将进入【等待重启】状态，灯光和遥测暂停。
  │    请确保您能到设备现场按 RESET 键重启。
  │    如果 10 分钟内未重启，设备将自动恢复旧配置。"
  │
  ├─ 用户确认 → PUT /api/devices/{id}/wifi-config
  │
后端
  ├─ 校验设备存在且 source=REAL
  ├─ MqttPublisher 发布到 streetlight/{id}/config
  ├─ UPDATE device SET restart_pending=1 WHERE device_id=?
  ├─ 记录 audit_log（操作人、时间、IP，不记录密码明文）
  └─ 返回成功
  │
EMQX → 硬件收到 config 消息
  ├─ 解析 JSON，提取 wifi_ssid + wifi_password
  ├─ config_save() 写入 Flash
  ├─ printf("[CFG] WiFi 配置已更新, 请按 RESET 重启设备\r\n")
  ├─ g_restart_pending = 1
  └─ return（不卡死）
  │
硬件主循环（g_restart_pending == 1）
  ├─ 停止遥测上报（publish_telemetry 直接 return）
  ├─ 停止边缘决策（edge_decision 直接 return）
  ├─ 红灯闪烁：三短闪 + 长灭，循环（"请重启我"信号）
  ├─ 启动 10 分钟倒计时
  │    ├─ 倒计时内按了 RESET → 设备重启 → 新 WiFi 连接 → g_restart_pending 清零
  │    └─ 倒计时超时未重启 → 放弃新配置 → 恢复正常运行（旧 WiFi）
  └─ 主循环不卡死，MQTT 重连被跳过
  │
后端心跳监控（HeartbeatMonitorTask）
  ├─ 设备停止上报 → 360 秒超时 → device.status = OFFLINE
  └─ 心跳监控正常逻辑，无需改动
  │
前端 Dashboard / 设备详情页
  ├─ 设备卡片显示：⏳ 等待重启（WiFi 配置已下发）
  ├─ 设备状态灯：灰色/黄色（区别于红色故障离线）
  ├─ 倒计时："剩余 8 分 32 秒，超时后自动恢复旧配置"
  └─ 【取消配置】按钮：撤销本次 WiFi 修改，立即恢复正常
  │
运维人员到现场按 RESET
  ├─ 设备重启，从 Flash 读取新 WiFi 配置
  ├─ WifiConnect(新SSID, 新密码) → 成功
  ├─ mqtt_connect() → 成功
  ├─ 发送心跳 + 上报遥测
  └─ 后端收到心跳 → device.status = ONLINE, restart_pending = 0
  │
前端 → 设备恢复在线 → 状态灯变绿 → "WiFi 配置已生效"
```

### 6.3 技术方案

#### 硬件侧

**smartlighting.c 改动**：

```c
// 新增全局标志
static int g_restart_pending = 0;
static uint32_t g_restart_deadline = 0;  // 超时时刻 (tick)

// 主循环开头加判断
if (g_restart_pending) {
    // 1. 停止遥测和边缘决策
    //    publish_telemetry() 内判断 g_restart_pending 直接 return
    //    edge_decision() 内同样判断

    // 2. 红灯"三短闪"提示
    led_blink_restart_pattern();

    // 3. 检查 10 分钟超时
    if (osKernelGetTickCount() > g_restart_deadline) {
        printf("[CFG] 重启超时, 放弃新配置, 恢复旧 WiFi 运行\r\n");
        g_restart_pending = 0;
        // 重新加载旧配置（新配置未生效，Flash 里是新的但因为没重启 WiFi 没变）
        // 恢复正常运行，mqtt_connect() 重新连上
    }

    // 4. 跳过 MQTT 重连尝试
    osDelay(500);
    continue;  // 不执行采集/决策/上报逻辑
}

// 在 message_arrived() 的 config 处理中:
else if (strstr(topic, "/config")) {
    // ... 解析 SSID/密码、config_save() ...
    g_restart_pending = 1;
    g_restart_deadline = osKernelGetTickCount() + 600 * 100;  // 10 分钟 (CMSIS-RTOS tick默认1ms)
    g_mqtt_connected = 0;
    NetworkDisconnect(&g_network);
    printf("[CFG] WiFi 配置已更新, 请按 RESET 重启设备 (10分钟超时自动恢复)\r\n");
}
```

#### 后端侧

**DeviceController.java 新增接口**（与第四节相同）：

```java
@PutMapping("/{id}/wifi-config")
@RequirePermission("device:control")
public Result<?> updateDeviceWifi(@PathVariable String id,
                                   @RequestBody DeviceWifiConfigRequest request) {
    Device device = deviceService.getById(id);
    if (device == null) return Result.fail("设备不存在");
    if (!"REAL".equals(device.getSource())) return Result.fail("仅支持真实设备");

    // 下发 config 到设备
    String json = String.format("{\"wifi_ssid\":\"%s\",\"wifi_password\":\"%s\"}",
            request.getWifiSsid(), request.getWifiPassword());
    mqttPublisher.publish("streetlight/" + id + "/config", json);

    // 标记等待重启（不清除 source/status）
    device.setRestartPending(1);
    deviceService.updateById(device);

    // 审计日志（不记录密码）
    auditLogService.log("UPDATE_WIFI_CONFIG", id, "操作人修改了设备WiFi配置");

    return Result.ok("配置已下发，请到现场重启设备");
}
```

**device 表新增字段**：
```sql
ALTER TABLE device ADD COLUMN restart_pending TINYINT DEFAULT 0 COMMENT '等待重启标志';
```

#### 前端侧

设备详情页 WiFi 配置区域：
- 输入新 SSID + 密码
- 二次确认弹窗（含 10 分钟超时提醒）
- 配置下发后：
  - 设备状态显示"⏳ 等待重启"（灰色/黄色）
  - 倒计时组件："剩余 X 分 X 秒，超时后自动恢复旧配置"
  - 【取消配置】按钮：调用 `DELETE /api/devices/{id}/wifi-config` 撤销

### 6.4 超时回退流程（设备侧）

```
g_restart_pending = 1, 倒计时 10 分钟
  │
  ├─ 有人按 RESET → 设备重启 → 新配置生效 ✅
  │
  └─ 10 分钟到, 无人按 RESET
       │
       ├─ 清空 g_restart_pending
       ├─ 恢复 publish_telemetry + edge_decision
       ├─ mqtt_connect() 用旧 WiFi 重新连上
       ├─ 后端收到心跳 → device.status = ONLINE, restart_pending = 0
       └─ 前端设备恢复在线 → "WiFi 配置已失效，请重新操作"
```

### 6.5 前端"取消配置"业务逻辑

用户可能在等待重启期间改变主意，需要撤销：

```
前端点击【取消配置】
  → DELETE /api/devices/{id}/wifi-config
  → 后端发一条特殊的 config 消息: {"cancel_restart":true}
  → 硬件收到后:
      g_restart_pending = 0
      恢复正常运行（WiFi 配置回退到修改前的值，因为还没重启新配置没生效）
  → 后端 UPDATE device SET restart_pending = 0
  → 前端恢复正常显示
```

实际上，因为硬件还没重启，WiFi 连接还是旧的，所以"取消"就是简单地把 `g_restart_pending` 清掉，恢复正常运行即可。不需要真的"回退 WiFi 配置"（因为新配置还没生效）。

### 6.6 注意事项

| 事项 | 说明 |
|------|------|
| 硬件不卡死 | `g_restart_pending` 期间主循环继续跑，红灯闪烁 + 倒计时，不进入 `while(1)` |
| 心跳自然离线 | 不需要后端主动改 status，心跳监控 360 秒超时自然标记 OFFLINE |
| 密码不落盘 | audit_log 和前端日志都不能记录 WiFi 密码明文 |
| 10 分钟超时 | 防止设备因无人重启而长期僵尸，超时后自动恢复 |
| 多次改配置 | 每次下发新 config 时重置 `g_restart_deadline`，以最后一次为准 |
